## Этап 2 — локальный дневник · Запланирован

Профиль и история параметров с датами, ручной ввод продуктов и еды, внутренний календарь приложения, редактирование задним числом, SQLite. Системный Календарь iOS не используем. Неизвестные сведения спрашиваем или оставляем пустыми.

Параметры расчёта нормы видны и редактируются: формула Миффлина — Сан-Жеора, исходные параметры тела и возраста, коэффициент активности, профицит/дефицит в процентах, белок в г/кг. BMR × активность и корректировка цели рассчитываются кодом; неполный профиль не получает выдуманную норму. Любая автоматическая смена целей требует подтверждения.

Первый способ ввода — вручную: продукт, КБЖУ на 100 г с этикетки, масса, при необходимости штрихкод текстом. Камера и сканирование штрихкода относятся к этапу 6. Приём пищи получает timestamp устройства с часовым поясом; тип предлагается по локальному времени и редактируется. Источник значений и способ определения массы сохраняются отдельно.

**Единое правило этапов 2, 5 и 6:** ИИ распознаёт продукт, массу и текст этикетки; все суммы, пересчёты порций, рецептов и итогов выполняет детерминированный код. `null` означает «нет данных», а не ноль. Для каждого нутриента видны единица, источник, приблизительность и полнота данных. Дневной итог сообщает количество нутриентов с данными; частичную сумму нельзя показывать как полный итог.

Отдельная задача этапа 2 — уведомление **в 07:00 по текущему локальному времени со сводкой за вчера**. Планировщик отделён от чата: разрешение уведомлений, часовой пояс, пересоздание расписания при его смене и при изменении записей. Сводка строится из SQLite кодом. Проверить актуальность заранее подготовленного содержимого при закрытом приложении; не обещать запуск JavaScript точно в 07:00. Если свежих данных нет, не выдавать старую сводку за вчерашнюю; открывать актуальный день внутри приложения. Основа расписания — [локальные уведомления Expo](https://docs.expo.dev/versions/v58.0.0/sdk/notifications/).

Экспорт и импорт JSON вводятся вместе с первым сохранением реальных данных. Экспорт включает версию формата, постоянные IDs, даты/часовой пояс, единицы, источники и версии пищевой ценности. Секреты не экспортируются. Импорт проверяется до изменения базы, создаёт резервную копию текущих данных и заменяет данные транзакционно после подтверждения. Ошибка не изменяет базу; повторный импорт не создаёт дубликатов.

## Этап 5 — помощник · Запланирован

**Первая задача: проверка выбранного провайдера ИИ. Выбор делает владелец перед этапом 5.**

Варианты: (а) HTTPS-мост Codex CLI на VPS с авторизацией по подписке и секретным токеном; (б) Gemini API напрямую из приложения. Домашнего ПК у владельца нет. Разные протоколы реализуются отдельными адаптерами, не предполагается универсальность одного Base URL.

Проверить доступность для аккаунта и региона, условия использования выбранного размещения, текст, фото, структурированный ответ, лимиты, ошибки и отсутствие автоматического платного резервного маршрута. Пока проверки не проведены, работоспособность и отсутствие дополнительных расходов не утверждать. Россия отсутствовала в проверенном 14.11.2026 [списке Gemini](https://ai.google.dev/gemini-api/docs/available-regions); состояние требуется проверить заново перед выбором.

Проверить веб-поиск помощника, если выбранный провайдер его поддерживает: возможность через конкретный адаптер, источники/ссылки, ограничения и стоимость. Не обещать эту возможность до проверки и не подключать запасной платный сервис автоматически.

Второй способ добавить еду — текст, например «гречка 200 г, 2 яйца». ИИ извлекает продукты, количества и единицы; неоднозначный размер/массу уточняет. Затем код сопоставляет подтверждённые продукты со справочными значениями, рассчитывает порции и итоги. Перед сохранением доступно исправление. Нельзя выдавать сумму, сгенерированную моделью, за расчёт приложения; правило этапа 2 сохраняется.

Настройки: тип провайдера, HTTPS Base URL, модель, ключ/токен и проверка подключения. Ключ хранится в Keychain, не в исходниках/логах/экспорте. Смена Base URL не отправляет старый ключ новому адресу автоматически.

При недоступности провайдера запросы и фотографии остаются в локальной очереди с повтором/отменой; дневник не блокируется. Повторы проверяются при открытии приложения. Не обещать постоянную фоновую работу iOS.

История читается через разрешённые функции приложения из SQLite. Модель готовит предложения; фактическую запись подтверждает приложение. Цели и программа изменяются только после подтверждения владельца. Не диагностировать дефициты и не назначать лечение.

## Этап 6 — питание по фото · Запланирован

Российские продукты, в том числе ассортимент «Пятёрочки» и «Магнита». **USDA и FatSecret не использовать.**

Третий способ добавить еду — фото блюда; также здесь появляется фото этикетки КБЖУ на 100 г и сканирование штрихкода. Модель только извлекает продукт, предполагаемую массу или текст этикетки. Значения проверяет владелец, все пересчёты и суммы выполняет код.

Порядок поиска упакованного продукта: **личная база → Open Food Facts → каталог магазина (если есть VPS) → фото этикетки**.

1. Личная локальная база продуктов по штрихкоду и собственных рецептов.
2. Штрихкод → Open Food Facts → личная карточка со штрихкодом и источником `off`.
3. Необязательный каталог «Пятёрочки»/«Магнита» на VPS с мостом ИИ → личная карточка со штрихкодом и источником `store`.
4. Нет карточки → фото этикетки «на 100 г» → извлечение ИИ → подтверждение → личная карточка со штрихкодом и источником `label`.
5. Без упаковки → встроенный русский справочник (`reference`); «Мой рецепт» (`recipe`) — ингредиенты, массы и выход готового блюда, расчёт на 100 г кодом.
6. Последний вариант — приблизительное распознавание продукта/массы ИИ с пометкой «примерно» (`ai`). Суммы по-прежнему считает код; отсутствующие исходные нутриенты остаются `null`.

Все найденные карточки сохраняются в личной базе с исходным источником и штрихкодом, если он известен. `store` означает именно каталог магазина, не подменяет `off` или `label`. Подтверждённые личные данные автоматически не заменяются.

Каталоги — необязательные адаптеры **только на VPS вместе с мостом ИИ**, без прямых запросов из приложения. Официальный публичный потребительский API для этой задачи не подтверждён; `pyaterochka_api` и `magnit-api` рассматриваются как кандидаты неофициальных интеграций, не гарантированная возможность. До реализации выбрать конкретные проекты/версии и проверить условия доступа, поиск по штрихкоду против поиска только по названию, наличие КБЖУ именно на 100 г, единицы, варианты товара и ограничения запросов. Поиск только по названию не считать точным совпадением штрихкода. При отсутствии VPS, поломке, блокировке или таймауте адаптера этот шаг пропускается, приложение и остальные источники работают дальше.

Неприменимые шаги пропускаются. У каждого нутриента хранится источник/версия/единица/основание расчёта; способ определения массы порции хранится отдельно. Неизвестное значение — «нет данных», не ноль. Микронутриенты похожего продукта нельзя подставлять в брендовый продукт незаметно. Обновление карточки не переписывает прошлые приёмы пищи. Итоги считает код, не модель.

Для [Open Food Facts](https://openfoodfacts.github.io/openfoodfacts-server/api/) сохранить атрибуцию/условия ODbL, обработать лимиты и проверить покрытие на реальных штрихкодах. Найденная карточка не гарантирует точность.
